# build-base

One nixpkgs, one Rust toolchain and one set of crate overrides, taken by every
repository as its `base` input, so a crate at one version and feature set has
one store path everywhere and the remote builder's store serves it to all.

A Cargo workspace commits a `Cargo.nix` generated by this base's crate2nix
(`nix run github:LiGoldragon/build-base#crate2nix -- generate`) and its flake is:

```nix
{
  inputs.base.url = "github:LiGoldragon/build-base";
  outputs = { self, base }: base.lib.workspaceOutputs { cargoNix = ./Cargo.nix; };
}
```

That gives one derivation per crate, registry, git and member alike, and per
member: `packages.<member>`, its build; `checks.<member>`, which runs the test
binaries its test build compiled and compiles nothing. A test build honours
the member's `[[test]]` targets as cargo does: a target whose
`required-features` the feature set lacks is left out, and a target with
`harness = false` is compiled as a plain binary whose own `main` the check
runs. `checks.cargo-nix`
proves the committed `Cargo.nix` is what this base's crate2nix generates from
the workspace: it compares Cargo.lock's packages with the crates Cargo.nix
records, then runs `crate2nix generate` offline in the sandbox over the source
with those crates vendored, each git source apart by its url and commit, so two
git sources of one crate name and version both resolve, and diffs the result
with the committed file.
Commit `crate-hashes.json` with `Cargo.nix`: the offline generation reads git
dependencies' hashes from it.

The base holds one version set for every crate a repository takes from another
repository, `crate-versions.json`: a registry crate (a locked package from a
registry) by name, the versions locked, one per crate except where the locks
carry semver-incompatible versions side by side; a git crate (a locked package
from a git repository) by name and version, the git revisions locked, each the
full commit after `#` in the lock's source. A workspace member, a path source,
is in no set. `checks.crate-versions` refuses a Cargo.lock that locks a
registry crate at a version outside the set or a git crate at a revision
outside it, naming each as `<crate>: lock <version> set <versions>` and
`<crate>: lock <version> <revision> set <version revision, ...>`. A version or
a revision moves once, here, and every active repository's lock moves with it.
The set is derived, never written by hand:

```sh
nix run github:LiGoldragon/build-base#crate-version-set -- <Cargo.lock ...>
```

writes `crate-versions.json` in the working directory from the given locks.
Where two locks carry semver-compatible registry versions of one crate that
differ, it names the crate, each version and its lock, and writes nothing.
Where the locks carry one git crate at more than one revision, it writes the
set whole, each revision held, and lists each such crate with the
repositories at each revision: that list measures the drift between the
repositories, and each repository follows the set to close it.

The base holds, beside it, one feature set for every such crate,
`crate-features.json`: by crate and version for a registry crate, by crate,
version and revision for a git crate, the features it is built with
(`features`) and the optional dependencies they attach (`attaches`). It
admits no exception: where the union attaches an optional dependency some
repository builds the crate without, that repository carries the edge, in
its manifest, lock and Cargo.nix; a repository that never builds the crate
carries none. Every crate the set holds is built with the set's features, its
optional dependencies those features attach and every crate beneath it under
its own set, whichever member, test build or repository reaches it
(`crate-builds.nix`, the function each Cargo.nix is imported with), so it has
one store path everywhere; features are additive, so the union of what each
repository asks builds for all. crate2nix writes a git crate's `src` as a
`fetchgit` carrying its `rev`, a registry crate's `sha256` and a member's
`src` as a local path, and the set tells the kinds apart by those
(`crate-identity.nix`). A crate the set lacks, or whose resolution asks a
feature the set does not hold, is built as its build resolves it, over
dependencies built from the set. `checks.crate-features` refuses a workspace
whose Cargo.nix resolves, for a crate it builds, a version or a git revision
the set lacks or a feature it does not hold, or lacks an optional dependency
the set's features attach, naming each crate. What a Cargo.nix resolves is
what crate2nix gives each crate when every member is built with all its
features and its dev-dependencies (`resolved-features.nix`). The set is
derived, never written by hand:

```sh
nix run github:LiGoldragon/build-base#crate-feature-set -- <repository>/Cargo.nix ...
```

writes `crate-features.json` from the given workspaces, each named by its
directory, as the union of what each resolves, and names each edge a
repository must carry: the repository, the crate, the features attaching the
dependency, and the dependency. Where a crate asks of another a feature the
other's set lacks, it names them and writes nothing.

`memberChecks` and `extraChecks` are functions of the build context (below)
with `workspace`, the imported Cargo.nix, `tests`, each member's test build,
`check`, the base's check of a member under a feature set
(`check "member" [ "default" "feature" ]`), and `doc`, rustdoc over a member's
library under a feature set with rustdoc flags, its dependencies linked as its
build links them, no cargo involved
(`doc "member" [ "default" ] [ "-D" "warnings" ]`, the documentation in
`$out/share/doc`), and `clippy`, clippy-driver over every target of a member
under a feature set, as `cargo clippy --all-targets` lints them: the member's
test build compiled by clippy-driver over the dependencies that build already
links, the member's `[lints]` (or the workspace's, where it takes them)
applied uncapped and the given flags after them, no cargo involved and
nothing but the member compiled
(`clippy "member" [ "default" ] [ "-D" "warnings" ]`). `memberChecks` gives, by member name, the check that stands in place of
the base's (a member whose tests need an environment), or null for a member
that has no check. `extraChecks` returns the repository's own further checks,
under names no member, `cargo-nix`, `crate-versions`,
`crate-features` or `default` has:

```nix
base.lib.workspaceOutputs {
  cargoNix = ./Cargo.nix;
  memberChecks = { pkgs, tests, ... }: { frozen-contract = null; };
  extraChecks = { pkgs, toolchain, workspace, tests, doc, clippy, ... }: {
    fmt = …;
    doc = doc "member" [ "default" ] [ "-D" "warnings" ];
    clippy = clippy "member" [ "default" ] [ "-D" "warnings" ];
  };
}
```

`packages.default` is every member and `checks.default` every check, the
repository's own included, so a green default is the whole gate.

A Cargo.nix kept apart from the workspace it was generated from (a pinned
dependency built per crate) takes the same freshness check from the context:

```nix
cargoNixCheck {
  source = <the workspace, holding Cargo.toml and Cargo.lock>;
  cargoNix = ./nix/dependency/Cargo.nix;
  crateHashes = ./nix/dependency/crate-hashes.json;
}
```

`lib.contexts.<system>` holds `pkgs`, `toolchain`, `crateOverrides`,
`crate2nix`, `buildRustCrateForPkgs` and `cargoNixCheck` for a flake that needs
more, and `lib.workspace.<system>`, given the same arguments as
`workspaceOutputs`, is one system's workspace, `packages`, `tests`, `checks`,
`devShell`, and `workspace` and `buildRustCrateForPkgs`, the imported
Cargo.nix and the function that builds its crates from the feature set, for a
flake that composes its own outputs; the context's own `buildRustCrateForPkgs`
knows no Cargo.nix and builds a crate as it is resolved. Cargo stays the
local loop: `nix develop`.

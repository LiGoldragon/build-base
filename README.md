# build-base

One nixpkgs, one Rust toolchain and one set of crate overrides, taken by every
repository as its `base` input, so a crate at one version and feature set has
one store path everywhere and the remote builder's store serves it to all.

A Cargo workspace commits a `Cargo.nix` generated by this base's crate2nix
(`nix run github:LiGoldragon/build-base#crate2nix -- generate`) and its flake is:

```nix
{
  inputs.base.url = "github:LiGoldragon/build-base";
  outputs = { self, base }: base.lib.workspaceOutputs { cargoNix = ./Cargo.nix; };
}
```

That gives one derivation per crate, registry, git and member alike, and per
member: `packages.<member>`, its build; `checks.<member>`, which runs the test
binaries its test build compiled and compiles nothing. A test build honours
the member's `[[test]]` targets as cargo does: a target whose
`required-features` the feature set lacks is left out, and a target with
`harness = false` is compiled as a plain binary whose own `main` the check
runs. `checks.cargo-nix`
proves the committed `Cargo.nix` is what this base's crate2nix generates from
the workspace: it compares Cargo.lock's packages with the crates Cargo.nix
records, then runs `crate2nix generate` offline in the sandbox over the source
with those crates vendored, each git source apart by its url and commit, so two
git sources of one crate name and version both resolve, and diffs the result
with the committed file.
Commit `crate-hashes.json` with `Cargo.nix`: the offline generation reads git
dependencies' hashes from it.

The base holds one version set for every crate a repository takes from another
repository, `crate-versions.json`: a registry crate (a locked package from a
registry) by name, the versions locked, one per crate except where the locks
carry semver-incompatible versions side by side; a git crate (a locked package
from a git repository) by name and version, its one git revision, the full
commit after `#` in the lock's source. A git crate has one revision per
version, and a version of it semver-compatible with another is refused, as for
a registry crate. A workspace member, a path source,
is in no set. `checks.crate-versions` refuses a Cargo.lock that locks a
registry crate at a version outside the set or a git crate at a revision
outside it, naming each as `<crate>: lock <version> set <versions>` and
`<crate>: lock <version> <revision> set <version revision, ...>`: the set's
revision for the lock's version, or its versions where it lacks that one. A version or
a revision moves once, here, and every active repository's lock moves with it.
The set is derived, never written by hand:

```sh
nix run github:LiGoldragon/build-base#crate-version-set -- <Cargo.lock ...>
```

writes `crate-versions.json` in the working directory from the given locks.
Where two locks carry semver-compatible registry versions of one crate that
differ, it names the crate, each version and its lock, and writes nothing.
Where the locks carry one git crate at more than one revision of a version, or
at two semver-compatible versions, it refuses likewise: it writes nothing and
lists every such crate with each version and revision and the repositories at
each. That list is the work queue: each repository moves to one revision, and
the set is generated when the list is empty. `checks.crate-version-set-one-revision`
proves the refusal on a fixture of two repositories locking one git crate
version at two revisions.

The base holds, beside it, one feature set for every such crate, or the named
sets below, `crate-features.json`, `{ "registry": …, "git": … }`: by crate and
version in each map (a git crate has one revision per version, so no revision
keys it), the union over every revision the given Cargo.nix files lock, the features it is built with
(`features`) and the optional dependencies they attach (`attaches`). It
admits no exception: where the union attaches an optional dependency some
repository builds the crate without, that repository carries the edge, in
its manifest, lock and Cargo.nix; a repository that never builds the crate
carries none. Every crate the set holds is built with the set's features, its
optional dependencies those features attach and every crate beneath it under
its own set, whichever member, test build or repository reaches it
(`crate-builds.nix`, the function each Cargo.nix is imported with), so it has
one store path everywhere; features are additive, so the union of what each
repository asks builds for all. crate2nix writes a git crate's `src` as a
`fetchgit` carrying its `rev`, a registry crate's `sha256` and a member's
`src` as a local path, and the set tells the kinds apart by those
(`crate-identity.nix`). A crate the set lacks, or whose resolution asks a
feature the set does not hold, is built as its build resolves it, over
dependencies built from the set. `checks.crate-features` refuses a workspace
whose Cargo.nix resolves, for a crate it builds, a version or a git revision
the set lacks or a feature it does not hold, or lacks an optional dependency
the set's features attach, naming each crate. What a Cargo.nix resolves is
what crate2nix gives each crate when every member is built with all its
features and its dev-dependencies (`resolved-features.nix`), member by member.

A feature is an input: a crate built with and without one is two builds. Where
a vision line places a feature per consumer, a crate holds named sets in place
of its union, written by hand in `crate-features.json`, each a deliberate entry:

```json
"signal": { "11.0.0": { "sets": [
  { "name": "plain", "features": [ … ], "attaches": [ … ],
    "vision": "vision:ethos, \"The datom traits are compiled in only where text is spoken\"" },
  { "name": "datom", "features": [ "datom", … ], "attaches": [ … ], "vision": "…" }
] } }
```

Every crate with named sets lists the same names in the same order. A build,
a member's, a test build or doc, takes the first name whose sets hold
what it resolves for every crate with named sets, and under that name each
such crate is built with its set of the name and every other crate with its
union over dependencies built under the same name, so a Nexus's signal and a
CLI's are two builds, each one store path everywhere, and no build links
both. `checks.crate-features` refuses a workspace a member of which resolves a
crate with named sets as no listed set holds, naming the member, the crate,
its features and the listed sets, or as no one name holds for all of them, or
lacks an optional dependency a set it may be built with attaches. The set is
derived, its named sets kept as written:

```sh
nix run github:LiGoldragon/build-base#crate-feature-set -- <repository>/Cargo.nix ...
```

writes `crate-features.json` from the given workspaces, each named by its
directory, as the union of what each resolves, and names each edge a
repository must carry: the repository, the crate, the features attaching the
dependency, and the dependency. It keeps the named sets the file holds,
writing their `attaches`, and never adds one: where a member resolves a crate
with named sets as no listed set holds, or as no one name holds for all of
them, it names the member, the crates, their features and the listed sets, and
writes nothing; named sets of a crate no workspace resolves are dropped, and
named. Where a crate asks of another, under any name, a feature the other's
set of that name lacks, it names them and writes nothing: a crate whose union
passes a per-consumer feature on takes named sets itself.
`checks.crate-features-named-sets` proves the check on fixtures: a set not
listed is refused, a listed second set passes.

A crate handed the same effective features is one derivation
(`crate-default-features.nix`). `default` names the features it implies, yet
buildRustCrate passes it to rustc as a feature of its own, so a crate reached
with and without default features, every implied feature otherwise on, would
be two builds. Every crate is handed `default` exactly where its [features]
table declares it and everything it implies is on, each feature in its closure
and each optional dependency it attaches; otherwise `default` is dropped.
crate2nix writes no empty `default`, so a crate whose `default` is empty, as
signal's, is built without it. `checks.crate-default-features` proves it on a
fixture crate through the base's buildRustCrate: an empty `default` with and
without default features is one derivation, `std` and `default std` are one,
and no feature and `std` stay two.

A crate is built from its source without what the build never reads
(`crate-source.nix`), for a member and for a git crate alike: in each directory
holding a Cargo.toml, `tests`, `benches`, `examples`, `.beads`, `.github`,
`Cargo.lock`, `Cargo.nix`, `crate-hashes.json`, `flake.nix`, `flake.lock`,
`rust-toolchain.toml`, `.gitignore` and Markdown are left out; `src/`,
`build.rs` and every other file stay, for a crate may `include_str!` or its
build script may read them. The remaining tree is copied to the store at
evaluation (`builtins.path`, named for the crate and its version), so its path
is decided by its content alone: the same crate at two commits that differ only
in a test, a README, a lock or a flake is one path and one build, and a crate
built in its own repository is the same path as that commit taken as a git
dependency. The fetchgit stays a fixed-output fetch; the copy is made over its
result, which is realised at evaluation, so the evaluation runs where the fetch
may. A root package is built as a git crate is, found by name in its source.
A member's test build reads its whole source, for a test may read the
repository's files.

`memberChecks` and `extraChecks` are functions of the build context (below),
its `buildRustCrateForPkgs` replaced by `buildRustCrateForPkgsFor`, the function
building the crates of one build from the feature set (below),
with `workspace`, the imported Cargo.nix, `tests`, each member's test build,
`check`, the base's check of a member under a feature set
(`check "member" [ "default" "feature" ]`), and `doc`, rustdoc over a member's
library under a feature set with rustdoc flags, its dependencies linked as its
build links them, no cargo involved
(`doc "member" [ "default" ] [ "-D" "warnings" ]`, the documentation in
`$out/share/doc`). Every test build is compiled by clippy-driver over every
target of its member, as `cargo clippy --all-targets` lints them, with the
member's `[lints]` (or the workspace's, where it takes them) applied uncapped
and `lintFlags` after them (an argument of `workspaceOutputs`, `[ "-D"
"warnings" ]` unless given): the one compilation is the lint gate and the test
build both, and a lint refused fails the member's test build and so its check.
The feature set a member is linted under is the feature set of its check
(`memberChecks` gives `check "member" [ "default" "feature" ]` to lint a
feature-gated line). `memberChecks` gives, by member name, the check that stands in place of
the base's (a member whose tests need an environment), or null for a member
that has no check. `extraChecks` returns the repository's own further checks,
under names no member, `cargo-nix`, `crate-versions`,
`crate-features` or `default` has:

```nix
base.lib.workspaceOutputs {
  cargoNix = ./Cargo.nix;
  memberChecks = { pkgs, tests, ... }: { frozen-contract = null; };
  lintFlags = [ "-D" "warnings" ];
  extraChecks = { pkgs, toolchain, workspace, tests, doc, ... }: {
    fmt = …;
    doc = doc "member" [ "default" ] [ "-D" "warnings" ];
  };
}
```

`packages.default` is every member and `checks.default` every check, the
repository's own included, so a green default is the whole gate.

A Cargo.nix kept apart from the workspace it was generated from (a pinned
dependency built per crate) takes the same freshness check from the context:

```nix
cargoNixCheck {
  source = <the workspace, holding Cargo.toml and Cargo.lock>;
  cargoNix = ./nix/dependency/Cargo.nix;
  crateHashes = ./nix/dependency/crate-hashes.json;
}
```

`lib.contexts.<system>` holds `pkgs`, `toolchain`, `crateOverrides`,
`crate2nix`, `buildRustCrateForPkgs` and `cargoNixCheck` for a flake that needs
more, and `lib.workspace.<system>`, given the same arguments as
`workspaceOutputs`, is one system's workspace, `packages`, `tests`, `checks`,
`devShell`, and `workspace` and `buildRustCrateForPkgsFor`, the imported
Cargo.nix and, given `{ packageId; features; runTests; }`, the function that
builds the crates of that build from the feature set under the set name it
takes, for a flake that composes its own outputs
(`builtRustCratesWithFeatures { …; buildRustCrateForPkgsFunc = buildRustCrateForPkgsFor { … }; }`); the context's own `buildRustCrateForPkgs`
knows no Cargo.nix and builds a crate as it is resolved. Cargo stays the
local loop: `nix develop`.
